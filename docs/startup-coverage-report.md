# 冷启动与测试覆盖率

分支 `v1/startup-and-coverage`，基于 main（16ff22a）。对应 PRD 第 14 节的两项非功能需求：

| 需求 | 目标 | 结果 |
| --- | --- | --- |
| 冷启动到可交互 | ≤ 3 s | **0.8–1.0 s**（Windows，本机） |
| 核心包测试覆盖率 | ≥ 80% | **行覆盖率 91.1%** |

## 冷启动

`npm run startup`（`apps/desktop/scripts/startup.mjs`）测的是打包后的应用，也就是用户实际运行的程序：
- **启动方式**：启动 5 次，每次用新建的用户数据目录，相当于安装后第一次运行。两次启动都开着 Chromium 的沙箱，和用户一样。
- **计时终点**：编辑器画出第一个项目的画布，并且又渲染了一帧，即“可以操作”。
- **Python 后端**：同时开始计时，单独报告。编辑器不等它。
- **口径偏保守**：时间里含有 Playwright 自身的启动开销，所以结果略偏悲观。
- **第一次启动单独列出**：刚打包出的程序，系统还没读过这些文件，Windows 还要做病毒扫描。这最接近真正的冷启动。

本机（Windows）结果：

| | 窗口出现 | 编辑器可用 | Python 后端应答 |
| --- | ---: | ---: | ---: |
| 刚打包后的第一次启动 | 513 ms | 1016 ms | — |
| 之后的启动（中位数） | 350 ms | 820–870 ms | 666 ms |

“刚打包后的第一次启动”那一行，Python 一列是空的：那一轮还没改成并行计时，测出的只是编辑器就绪后的第一次应答。改过之后，后端在编辑器可用之前就已经能应答。

## 测试覆盖率

`npm run coverage` 用 V8 统计 `packages/core/src` 的覆盖率，行覆盖率低于 80% 时失败。

| | 语句 | 分支 | 函数 | 行 |
| --- | ---: | ---: | ---: | ---: |
| 补测试之前 | 83.7% | 71.9% | 86.7% | 88.0% |
| 补测试之后 | 86.7% | 74.1% | 89.5% | **91.1%** |

补测试之前已经达标，没有为了数字去补。补的是 `edit.ts`（原来行覆盖率 32.5%）和 `project.ts`（57%）里编辑器依赖、但没有任何测试覆盖的行为。新增的测试在 `test/editing.test.ts`，共 11 个：

- **加节点**：名字不重复；新的输入、输出排在 `forward()` 签名和返回值的末尾。
- **连线**：一个输入端口只接一条边，再连会替换旧的；会形成环的连接被拒绝。
- **删节点**：删除节点时连带删掉它的边和它在接口中的位置；可变长端口重新编号，不留空位。
- **参数**：设为 `undefined` 时回到默认值。
- **模块嵌套**：模块不能放进自己，也不能放进它包含的模块。
- **下钻路径**：中间的实例被删除后，路径只保留到仍然存在的那一层；能找到通往某个模块的最短下钻路径。
- **命名**：新模块的类名和 id 不与已有的重复。
- **接口变化**：模块删掉一个输入后，上层连到这个端口的边被去掉。
- **打开文件**：拒绝更新版本 NeuroLoom 保存的文件，并说明原因；拒绝入口模块不存在的文件。

为了确认这些测试真的守住了行为，我分别临时改坏了三处实现，每次都恰好有一个测试失败：
- 去掉“一个输入只接一条边”；
- 去掉嵌套检查；
- 去掉可变长端口的重新编号。

分支覆盖率仍然较低（74.1%），主要是形状推断和节点规格里的错误分支。这些在“每个节点规格与 PyTorch 往返”的测试里有整体验证，这次没有逐个补。
